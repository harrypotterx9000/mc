# 技术决策记录（DECISIONS）

> 每条决策只增不改；被推翻时新增一条并注明取代关系。

## ADR-001 独立静态站点运行

- 日期：2026-11-06
- 决策：项目以静态站点方式运行（`index.html` + `js/`），本地用零依赖 Node 静态服务器，仅绑定 `127.0.0.1`。
- 理由：原游戏即 90 个脚本 + 数据文件，无构建步骤；静态服务满足 Worker/`fetch` 的同源要求。
- 影响：后续服务器只承担多人逻辑，不负责页面托管（可由同一进程提供，但不是必须）。

## ADR-002 移除 B 站重定向，保留原始版本标签

- 日期：2026-11-06
- 决策：为了让页面能在 B 站 iframe 之外启动，删除 `index.html` 中唯一一行 Toy 重定向脚本；其余字节不变。
- 理由：该脚本会把任何直接访问跳回 bilibili.com，导致本地不可用。
- 保护：删除前的完整源码提交为 `v0.0.0-original`，并另有 zip + SHA-256 清单。
- 影响：这是初始化阶段唯一的源码改动，已在 CHANGELOG 记录。

## ADR-003 无账号访客模式

- 日期：2026-11-06
- 决策：删除 B 站登录与账号体系；玩家用昵称 + 服务器分配的临时 ID；用邀请码进房间；不建任何注册/登录。
- 理由：见 PROJECT_SPEC §3/§6；避免永久身份带来的隐私与合规负担。
- 影响：云存档（按账号）取消；皮肤/披风改为直接开放；联机不再有解锁门槛。

## ADR-004 服务器权威 + 双存档

- 日期：2026-11-06
- 决策：多人世界由自建服务器模拟与存档；单人世界继续用浏览器 IndexedDB；两者互不覆盖。
- 理由：多人需要一致性与反作弊；单人应离线可玩。
- 影响：需要新增服务器世界实例与协议；客户端 `NetClient` 复用现有消息词汇。

## ADR-005 Git 导入与分支模型

- 日期：2026-11-06
- 决策：`main` 稳定、`develop` 集成、`phase/*` 阶段分支；初始化基线打 `v0.1.0-preproject`；原始源码打 `v0.0.0-original`。
- 理由：阶段化开发需要可回滚的清晰历史；原始版本必须可随时对照。
- 影响：合并需要用户确认；禁止强推与历史重写。

## ADR-006 按字节保存源码

- 日期：2026-11-06
- 决策：仓库设置 `core.autocrlf=false` 并加 `.gitattributes`（`* -text`）。
- 理由：原始 JS 为 LF；Windows 默认转换会让"原始字节"无法验证。
- 验证：`v0.0.0-original` 的 blob 与原文件 SHA-256 一致。

## ADR-007 远程仓库以远程现状为准

- 日期：2026-11-06
- 决策：`https://github.com/harrypotterx9000/mc` 当前只有 1 个 README 提交，与本地历史无关；首次推送采用**新分支 + PR**，不改远程 `main`，不允许强推。
- 理由：避免覆盖远程内容或制造不可逆历史。
- 状态：已执行（见 ADR-008）。

## ADR-008 首次远程推送采用新分支 + PR

- 日期：2026-11-06
- 背景：本地历史与远程 `main` 无共同祖先（远程仅 `6c476c0` README）。
- 决策：`git push -u origin main:opusmc-init`，远程新增 `opusmc-init` 分支；PR 由用户在 GitHub 上创建并合并；远程 `main` 在合并前保持不变。
- 结果：`opusmc-init` 已推送（`791d16b`），远程 `main` 仍为 `6c476c0`；GCM 已有可用凭据，未出现交互弹窗。
- 影响：本地 `main` 跟踪 `origin/opusmc-init`；PR 合并后需把 `origin/main` 拉回并重新对齐跟踪关系。


## ADR-009 未验收改动不保留

- 日期：2026-11-06
- 决策：阶段改动只有在用户明确验收通过后才提交；未验收的代码、文档、暂存区、stash、补丁与临时分支一律丢弃，不跨阶段保留。
- 背景：phase-01 的改动在用户指示"先不要开始阶段 1"后被整体丢弃（stash/补丁/临时目录/阶段分支全部删除）。
- 影响：后续阶段必须"实现 → 用户验收 → 提交"；不得用 stash 长期保存半成品。

## ADR-010 开发基线以 PR #1 的整合提交为准

- 日期：2026-11-06
- 背景：PR #1 由用户以 `opusmc-integration`（`2798c08`）创建，文件内容与本地导入一致，但历史不同（基于远程 `main` 的单次整合提交）。
- 决策：本地 `develop` 对齐 `2798c08` 并作为开发基线；本地 `main`（`e636804`）仅作历史存档，PR 合并后再对齐 `origin/main`。
- 影响：阶段分支从 `develop`（`2798c08`）创建；不再基于早期导入历史开发。

## ADR-011 阶段 0 复核结论与阶段 1 边界

- 日期：2026-11-06
- 背景：阶段 0 只读复核完成；用户确认 10 项改造决策，并指定阶段 1 采用 1-A。
- 决策：
  1. **保留 `e49a54c` 作为当前 HEAD**（仅文档提交）；代码基线仍为 `2798c08`；阶段分支从当前 `develop` 创建。
  2. 阶段 1 **先更新 `PROJECT_SPEC.md` §6**，加入“欢迎来到 OpusMC（用户协议窗口）”和“你是哪种玩家？”两个界面的删除，再改代码。
  3. 披风只开放**普通 7 款 + 活动款**；管理员款（`adm*`）保持隐藏。
  4. 删除签到/活动时，企鹅、金苹果等活动款装饰**随活动一起删除**；最终只留普通 7 款。
  5. 删除“你是哪种玩家”后，**新世界默认关教程**；旧存档 `meta.tutorial` 保留原值；情景提示 `settings.tips` 不受影响。
  6. 阶段 1 只删“选项入口 + 反馈面板”；**保留 `Telemetry` 核心与 `GAME_BUILD`**，遥测模块整体清理留到后续阶段。
  7. 服务端采用 **B/C 混合**：协议词汇与区块 RLE 编码复用 `p2p.js`，传输换 WebSocket；`NetClient` 保留为“直连原版代理”的遗留功能。
  8. 服务端允许引入 `ws`（唯一依赖）。
  9. 阶段 8 **先交付 LAN**；HTTPS/WSS 与公网作为后续，不提前标记完成。
  10. 本地 `cloud` 元数据与 `mcjs-cloud-dirty-*` **原样保留**；每月手动/脚本清理一次，不自动删除。
  11. 阶段 1 采用 **1-A**：删除 `UnlockScreen` 的同时让 `onlineGate()` 直接放行，避免活引用；这会提前完成阶段 2 的多人门槛部分。
- 影响：
  - 阶段 1 的删除清单需要同时处理 `social.js:31` 的 `FeedbackScreen` 引用，并保留 `telemetry.js` 的 `GAME_BUILD`。
  - 阶段 2 只剩皮肤/披风/装饰开放与相关渲染/保存迁移；多人门槛已在阶段 1 按 1-A 处理。
  - 阶段 3 删除账号/云存档/公告/签到；活动款装饰随签到一起删。
  - 阶段 5 不追求兼容原版 Java 代理协议；`NetClient` 仅保留遗留直连。
- 状态：**已确认；阶段 1 尚未执行**。
