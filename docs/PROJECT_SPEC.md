# OpusMC 项目总规范（PROJECT_SPEC）

> 本文件是 OpusMC 项目唯一的长期总规范。所有阶段的目标、边界与验收均以本文件为准；
> 与本文件冲突的临时需求必须先更新本文件再实施。
>
> 版本：1.6（2026-11-12，phase-05 自建服务器实现、测试与修复复核完成并已验收）
> 状态：生效

## 1. 项目定位

OpusMC 是一个**独立运行的浏览器体素游戏**，由原 B 站 Toy 平台版本改造而来：

- 完全脱离 Bilibili Toy 平台，不再依赖任何 B 站身份、接口或页面容器。
- 通过普通浏览器直接访问，无需安装专用客户端。
- 支持电脑、手机和平板。
- 保留原有 WebGL2 渲染体系与全部游戏内容。

## 2. 非目标（明确不做）

- 不做游戏账号系统：**不开发注册、登录、密码、账号资料、账号绑定、找回密码**。
- 不做永久身份体系：没有"账号"，只有昵称 + 服务器分配的临时玩家 ID。
- 不做账号绑定式云存档（原 `/api/cloud/*` 一类的按账号同步）。
- 不向玩家传输游戏画面（不做云游戏/像素流）。
- 不重写游戏引擎；以现有脚本模块为基础迭代（phase-05 后页面加载 87 个脚本、`js/` 91 个 `.js`）。

## 3. 玩家身份：无账号访客模式

| 项 | 规则 |
|---|---|
| 身份 | 玩家首次进入时自行设置**昵称**；服务器分配**临时玩家 ID**（会话级，可随房间结束失效） |
| 账号 | 不存在账号、密码、邮箱、手机号、第三方登录 |
| 唯一标识 | 临时 ID 由服务器生成；不跨设备、不跨会话持久化；断线/刷新后可在服务器恢复窗口内用会话令牌恢复同一会话 |
| 多人加入 | 通过**房间邀请码**加入；房主创建房间后获得邀请码；邀请码由服务器生成，不提供公开房间列表 |
| 昵称约束 | 长度与字符集由服务器校验；重名由服务器消歧（如追加序号）；昵称不是身份，不参与权限判断 |
| 持久化 | 仅房间内有效；房间关闭后身份不再保留 |

## 4. 服务器与客户端分工

自建服务器运行在项目所有者的电脑上（局域网/公网入口由部署决定）：

服务器负责：
- 多人世界管理（房间生命周期、邀请码、人数上限、房主/踢出、关闭）
- 临时玩家身份管理（昵称校验与消歧、临时 ID、会话令牌、断线恢复）
- 游戏状态同步（玩家位置/视角/状态/外观、方块变更、方块实体、掉落物、时间天气）
- 基本游戏规则校验（移动/破坏/放置/权限的合法性；服务端权威，但不要求完整物理/战斗/物品语义模拟）
- 多人世界存档（服务器硬盘；seed + 方块覆盖层 + 玩家状态 + 方块实体）
- 静态网页资源、WebSocket、日志、备份、运行状态、正常启动/关闭

客户端负责：
- WebGL2 渲染
- 玩家输入
- UI
- 摄像机
- 本地画面与动画表现
- 地形确定性生成（使用服务器 seed）、本地生物/红石/流体模拟、合理的本地预测

**服务器不向玩家传输游戏画面。** 服务器不做生物 AI/红石/流体/战斗的完整模拟；这是 phase-05 的
明确边界（见 ARCHITECTURE §14.3、KNOWN_ISSUES K-67/K-69）。

## 5. 双存档

| 存档 | 位置 | 说明 |
|---|---|---|
| 单人世界 | 浏览器 IndexedDB | 保持现有 `mc-js-clone` 结构；换设备不迁移 |
| 多人世界 | 服务器硬盘 | 由服务器写入与恢复；客户端不持有权威副本；保存 seed + 方块覆盖层 + 玩家状态 |
| 云存档 | **取消** | 不再使用账号绑定式云存档 |

两种存档独立管理，互不覆盖。phase-05 的自建房间用 `srv~<邀请码>` 世界标识，**不写入**单人 IndexedDB；
服务器存档/备份/恢复说明见 `server/README.md`。

## 6. 功能改造清单（阶段 1–3 执行）

必须删除 / 关闭：

1. 主菜单公告面板（悬挂公告牌入口、未读角标、公告自动弹出）。
2. 主菜单「解锁披风和联机」面板。
3. 选项菜单中的「遥测数据」「制作人员名单与致谢」「用户协议和隐私说明」入口。
4. 主菜单指定文字（原 B 站/Toy 相关文案，具体清单在 phase-01 PLAN 中冻结）。
5. 「反馈问题」面板。
6. 登录、注册、账号资料、账号绑定相关界面与入口。
7. Bilibili / Toy 身份依赖（`Toy.*` 调用、B 站登录、关注/三连解锁、邀请分享桥）。
8. 进入主菜单前的「欢迎来到 OpusMC」用户协议/隐私窗口与「你是哪种玩家？」选择界面。

必须开放：

9. 所有皮肤、披风、装饰直接可用（不再有解锁条件；包括 `adm*` 管理员披风与签到活动款；无账号也可保存/恢复本设备外观）。
10. 多人游戏取消原有解锁限制（关注/三连/登录门槛）；房间加入仍由邀请码/房间服务控制。

约束：**严禁新建任何游戏账号系统**；删除后的空位不得用新账号 UI 填补。

## 7. 性能目标

| 端 | 目标 |
|---|---|
| 电脑 | 优先稳定 60 FPS |
| 手机 | 优先稳定 30 FPS；中高性能设备争取 60 FPS |
| 服务器 | 保留 20 TPS 房间/世界时钟与同步调度；不要求完整无头游戏模拟 |

同时要求：
- 保留原有丰富游戏内容，不为性能删内容。
- 提供分级画质（沿用现有 5 档光影 + 画质预设）。
- 优化区块生成、Worker、GPU、内存、网络同步。
- **所有性能结论以真实设备和真实测试为准**；无实测的数据只能标记 NOT MEASURED。

## 8. 阶段与 Git 管理

### 分支模型

- `main`：稳定版本，只在发布时由 `develop` 合并。
- `develop`：开发集成分支。
- `phase/*`：阶段开发分支，从 `develop` 创建。

### 固定流程（每个阶段）

1. 读 `PROJECT_SPEC.md`、`ARCHITECTURE.md`、`DECISIONS.md`、`STATUS.md`、`KNOWN_ISSUES.md`、上一阶段 `HANDOFF.md`。
2. 检查当前分支、提交、工作区。
3. 只做本阶段任务，不擅自跳阶段。
4. 验收：代码、功能、跨模块依赖、Monkey Patch、控制台、资源、回归。
5. 更新文档（STATUS/ARCHITECTURE/DECISIONS/CHANGELOG/KNOWN_ISSUES/TEST_REPORT/HANDOFF）。
6. 用户确认阶段验收 → 自动提交 Git。
7. **合并到 develop 必须用户确认；develop → main 必须用户确认。**
8. 禁止强推、禁止未经确认的历史重写、禁止删除远程分支。

### 版本标签

- `v0.0.0-original`：原始源码（未改动）。
- `v0.1.0-preproject`：初始化完成基线。
- 发布版本：`vX.Y.Z`，由 `main` 打标签。

## 9. 验收定义

- 没有实际测试的功能一律标记 **NOT TESTED**，不得写成可用。
- 结论必须区分：已验证事实 / 推断 / 未确认。
- 文档、代码、Git 提交、测试报告必须一致。

## 10. 远程仓库

- 目标：`https://github.com/harrypotterx9000/mc`
- 认证：使用 Git Credential Manager 或 GitHub CLI 交互授权；**PAT 不得出现在代码、文档、URL、提交、日志、聊天中**。
- 首次推送前必须确认远程现状与历史关系，并取得用户确认；禁止 force push。
